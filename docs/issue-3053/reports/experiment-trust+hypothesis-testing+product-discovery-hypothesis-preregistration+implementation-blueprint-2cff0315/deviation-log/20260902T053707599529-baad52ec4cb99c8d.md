# Deviation — two harness bugs found and fixed mid-run

actor: experiment-trust+hypothesis-testing+product-discovery-hypothesis-preregistration+implementation-blueprint-2cff0315
issue: 3053
when: 2026-09-02T05:37Z

## What was deviated from

`docs/issue-3053/decisions/pre-registration.md`, written before any pair was
run for real, registered a plan of: apply the mount fix (`--plugin-dir`) and
re-pin already identified by PR #3065, re-run all 4 pairs once, score them,
and report. It assumed the already-mount-fixed `run_pair.sh` would otherwise
run correctly.

## What was done instead

1. The first real invocation of all 4 pairs (relative `<output-root>`) failed
   all 8 arms at the `claude -p` step itself (exit 1, no session log, no
   deliverable): `run_arm()` redirects to `"$pair_dir/$arm.session.jsonl"`
   after `cd`-ing into the per-arm workspace, so a relative `<output-root>`
   resolves the redirect against the wrong cwd. Fixed by resolving `pair_dir`
   to an absolute path immediately after `mkdir -p`, in the same commit as
   the mount fix's follow-up. All 4 pairs re-run from scratch under this fix.
2. canonical: `git status --short` run this session after that path-fixed
   run, showing an untracked `DELIVERABLE.md` at this repo's own top level.
   In that run, 2 of 4 skills-off arms (01-study-groups, 03-review-scheduler,
   identified via each pair's own `skills-off.session.jsonl` `tool_use`
   entries) resolved "the repo root" to this orchestrating session's own
   working directory instead of their own clone: 01's arm `Write`'d
   `DELIVERABLE.md` there; 03's arm additionally `Read` (not wrote, per `git
   diff --stat README.md` showing no change) this session's own `README.md`
   and auto-memory `MEMORY.md`. Fixed by stripping every `CLAUDE_*`/
   `MUSTER_*` env var from the child `claude -p` process via `env -u ...`.
   Both affected pairs (both arms) re-run from scratch under this fix; the
   other 2 pairs were unaffected and not re-run.

## Why

Neither bug was anticipated by the issue, by PR #3065's own smoke test (which
used `--tools "Read"` on a trivial prompt that never explored the
filesystem), or by this session's pre-registration. Both were discovered by
inspecting the harness's own output (exit codes, `git status --short`, raw
`tool_use` entries) rather than trusting that a mount fix alone was
sufficient. Fixing them in place and re-running kept the pre-registered
metric/threshold/decision rule unchanged -- neither is a post-hoc
adjustment to the rule after seeing a result, since no scoring had occurred
yet in either case.
