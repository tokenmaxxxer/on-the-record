Expected: with `seed_arm_credentials()` in place, both arms of pair
`01-study-groups` (issues #19/#20) to reach `watched-to-completion`.

What actually happened instead: dispatch succeeded for both arms
(`dispatch_returncode: 0`), but `watch` itself failed
(`status: "watch-failed"` both arms, stderr "기록 없음 -- 아직 스폰된 적이
없다"). Root cause, confirmed by reading `spawn.py` (~line 2511): every
`--skills` dispatch always assigns a fresh lease-disambiguated session
name (`f"{skill_slug}-{disambiguator}"`), never the bare skill name --
`run_pair.py::execute_arm()` was calling `spawn.py watch --session
<bare skill name>` (the same pattern `scripts/issue-3127/
run_consumer_pair.py` already used, so this is an inherited defect, not
new to this round), which can never match. `gh pr list` confirms the
"on" arm's real session did complete and open a real PR (`#26`,
`issue-19/product-discovery-hypothesis-preregistration-dae6a96f`) despite
`run_pair.py` never observing it. The "off" arm (issue #20) has no PR:
its own auto-armed internal watcher (`ps`, PID 339098, `--session
product-discovery-hypothesis-preregistration-d12c5b1a`) was still running
when checked, and its isolated HOME (`/tmp/consumer-path-off-home-
ume6shqm`) shows partial deletion -- `prepare_arms._cleanup()` ran
`shutil.rmtree()` on that HOME immediately after `execute_arm()`'s failed
`watch` call returned (bounded by the default 5-minute stall-timeout
retry ceiling, not by the real session finishing), i.e. while the off
arm's real session was very likely still actively using that HOME.

Consequence for this issue's deliverable: this pair's result is not
recoverable from this attempt -- the off arm's session was interrupted by
its own HOME being deleted out from under it, and neither arm's
manifest/transport from this attempt can be reused (both arms must
restart with fresh HOMEs). Fixed in `run_pair.py::execute_arm()`: `watch`
is now called without `--session`, letting `events._lookup_roster_entry()`
match by `--issue`/`-C repo` alone and auto-select the single live match
(the same fallback `spawn.py watch`'s own usage text documents `--session`
as optional for) -- this should also close the cleanup-timing race as a
side effect, since `watch` will now correctly block until the real
session's `session-end` event rather than returning early on its own
lookup failure. Residual, not fixed this round: if a real session
genuinely exceeds `watch_timeout_s` (1800s default) or `_watch()`'s own
stall-timeout for a legitimate reason (slow model, retries), `run_pair()`
still calls `prepare_arms._cleanup()` immediately afterward regardless,
which could still delete a still-running session's HOME in that narrower
case -- named as an open finding in this round's own record, not
addressed here.
