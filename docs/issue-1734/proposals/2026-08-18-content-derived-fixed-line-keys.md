## Request
`on-the-record/monitors/poll-heartbeat.sh`'s delta-suppression keying loop (lines 244-291) keys every line matching none of `TAG_RE`/`ENTRY_RE`/`BULLET_RE` as the literal string `"__fixed__"`, disambiguating same-tick repeats by appending an appearance-order ordinal (`__fixed__~1`, `__fixed__~2`, ...). The diff loop then compares each key's current text against `prev_lines[key]` from the last tick. Because these ordinals are assigned by position, not content, inserting or dropping one such line at tick N shifts every following unkeyed line onto a different ordinal at tick N+1 — each shifted line then gets compared against a *different* line's previous text and is classified "changed" even though its own content never moved. Every falsely-"changed" line re-emits and wakes the orchestration session for a full model turn. Replace the ordinal keying with a content-derived key (leading `[tag] name:` prefix when present, plus a hash of the full line for stability and uniqueness; hash of the full line alone when no bracket-tag prefix exists) so a line's key travels with its own content instead of its position in the block; same-tick collisions keep the existing ordinal disambiguation, now reached only when two lines in the same tick are byte-identical.

## Constraints

- The same-tick collision-disambiguation block (lines 282-289, the `while f"{key}~{n}" in curr" ...` loop) is reused as-is, unedited — it already operates generically on whatever `key` was just assigned above it.
- `on-the-record/monitors/poll-heartbeat.sh:333`'s `healthy = sum(...)` filter, the only other site naming the literal `"__fixed__"` key (per survey.md's grep), is updated in the same commit so the ~30-minute aliveness heartbeat's "N session(s) tracked" count keeps excluding fixed-class lines under the new key prefix.
- Any edit inside the heredoc (lines 233-347) is re-checked with `bash -n on-the-record/monitors/poll-heartbeat.sh` before landing, per the file's own documented bash-3.2 heredoc-parsing landmine (survey.md).
- Issue #1732 (open, unmerged per survey.md) touches the same `to_emit`/heartbeat block but different lines (326-341, not 244-291/333); no coordination needed beyond an ordinary rebase if either lands first.

## Rationale
Two ways to derive a content key for the unkeyed-line class were considered — and a phase-1 hunt pass (docs/issue-1734/reports/implementation/2026-08-18-hunt-content-derived-fixed-line-keys.md) forced a revision of the first, described below:
1. **Chosen (revised after the hunt finding)**: try a broader bracket-tag pattern (`^\[([^\]]+)\]\s*([^:]+):`, any tag, not just `TAG_RE`'s enumerated set) first; when it matches, key as `fixed:{tag}:{name}:{sha256(line)[:12]}` (tag+name prefix *plus* a hash of the full line); when it does not match, key as `fixed:hash:{sha256(line)[:12]}`. The tag+name prefix keeps `runs/poll_heartbeat_last_state.json` greppable, mirroring the existing `TAG_RE`/`ENTRY_RE` convention (`watchdog:board-sweep`, `entry:issue-x`, ...) — but the prefix alone is not enough: the hunt found that `spawn.py`'s `_board_wide_sweep_all` (spawn.py:3066-3103) wraps each roster-target repo's watchdog output as `f"[{label}] {line}"` (spawn.py:3102), so a repo's independently-gated `[watchdog] board-sweep: ...` sub-messages (e.g. the delta-probe line at spawn.py:3260, the carryover line at spawn.py:3266, the budget-exceeded line at spawn.py:3338, which can co-occur in one tick) all derive the *same* `fixed:{label}:[watchdog] board-sweep` prefix — a real, already-shipped line family, not a hypothetical. A tag+name-only key would collapse these into one same-tick collision group, disambiguated by the kept ordinal block, reproducing this issue's own position-shift bug one layer down whenever one of the co-occurring sub-messages is silent on a later tick (reproduced live: docs/issue-1734/reports/implementation/2026-08-18-hunt-content-derived-fixed-line-keys.md's `python3 /tmp/repro1734/keying.py` output). Appending the full-line hash makes each *distinct* message's key unique on its own — same-tick collisions among genuinely different board-sweep sub-messages never happen — while a byte-identical line across ticks still re-derives the identical key (hash unchanged) and is still suppressed. Re-run against the same repro after adding the hash suffix (this session): both surviving tick-2 lines compare `changed=False` and are correctly suppressed.
2. **Rejected**: hash the full line text unconditionally for every unkeyed line, with no bracket-tag prefix at all (`fixed:hash:{sha256(line)[:12]}` always). This does not have the collision problem either — the hunt's repro would resolve correctly under this scheme too, since each distinct message's hash already differs — so the two schemes are now equivalent on correctness. It was rejected purely on legibility: an operator (or a future debugging session) reading `runs/poll_heartbeat_last_state.json` would see only hex strings for the entire unkeyed-line class instead of the tag+name context the rest of the file already provides for `TAG_RE`/`ENTRY_RE` keys, undermining the exact debuggability the issue's own bug report relied on (its reproduction quotes that state file's keys directly). The chosen scheme keeps that legibility for the tagged majority of unkeyed lines at the cost of one hash computation already being made regardless.

## Accumulation
This is a one-time keying-scheme change to a single `else` branch inside one heredoc, not a repeated per-file or per-entry pattern: `FIXED_TAG_RE`/`hashlib.sha256` is defined and used exactly once, at the one point in `poll-heartbeat.sh` where unkeyed lines are classified, mirroring how `TAG_RE`/`ENTRY_RE`/`BULLET_RE` already have exactly one definition and one call site each. There is no `roles/*.json`-style repeated-file pattern here and no inline `subprocess`/`gh` call being added — the change touches the same two lines (the `else` branch and the `healthy` filter) regardless of how many more unkeyed-line variants a future report happens to contain; nothing about this fix scales with N.

## Phase-1 hunt finding and resolution
The end-of-phase-1 warrant hunt (`docs/issue-1734/reports/implementation/2026-08-18-hunt-content-derived-fixed-line-keys.md`) found that the first draft's `fixed:{tag}:{name}` key (no hash suffix) derives the identical key for `spawn.py`'s multi-board `[watchdog] board-sweep: ...` sub-messages once wrapped by `_board_wide_sweep_all` (spawn.py:3102), reproducing this issue's own position-shift bug inside the new keying scheme whenever one of several same-tick sub-messages is silent on a later tick. Resolution: append a hash of the full line to the tag+name prefix (Rationale item 1, revised); re-run against the hunt's own repro (this session) shows both scenarios in its tick-2 case now compare `changed=False` and are correctly suppressed. This proposal's `## What will be done` and `## Rationale` sections above already reflect the resolved design — no further action needed before phase 2.
