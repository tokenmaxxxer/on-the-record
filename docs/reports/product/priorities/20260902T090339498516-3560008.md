Operator goal sentence restated this session (source: this issue's own
body, quoting the operator's morning framing): "방법론들을 제대로
활용해가면서 빠르고 효율적으로 산출물들을 만들어내는 것" — using
methodologies properly *and* producing deliverables quickly and
efficiently. Every prior measurement in this line of work (#3053 and
earlier) covered only correctness; speed/efficiency had never been
measured. This issue is the first to require reporting quality,
wall-clock-to-landed, token cost, and verification burden together, per
arm, rather than quality alone.

Standing instruction, reusable beyond this issue: verification-round
count (how many rounds a PR needed before landing, and how many defects
each round found) is treated as potentially the most informative single
metric — fewer rounds in a treatment arm is a real efficiency gain a
quality-score comparison alone would miss; the same-or-more case means a
layer is costing time without buying correctness. Any future A/B-style
comparison of process/tooling changes in this repo should carry this
metric alongside quality, not quality alone.

Standing instruction: selection quality (whether an orchestrator's
skill-picking judgment is good) is explicitly part of the product being
measured in these experiments, not a nuisance variable to standardize
away — restated from issue #3053 and reinforced here for any future
consumer-path measurement in this line.

Methodological standing rule, restated and now with a concrete instance:
a null result must always state what effect size the sample could have
detected, never be reported as bare "no effect." This session's own
result (a non-null "not measured" state, since no live run occurred) was
held to the same discipline — the results JSON's power statement
describes what the registered n=2 design would have been able to detect,
even though it never ran.
