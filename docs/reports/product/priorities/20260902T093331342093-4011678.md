The spawner stated verification-specific principles while asking for an independent grading of PR #3133's layers 1/2, distinct from (and narrower than) the implementation-side priorities the sibling PR #3133 session already captured for the same issue:

1. **A test double that fakes the trigger condition only proves the reaction logic, not that the trigger fires in production.** "start the loop, move HEAD under it... Do this against the real script, not a stub." The PR's own gate probes and unit tests all drive `watchdog_rc` via a fake `spawn.py` that hardcodes the exit code — none of them exercise the real `git fetch`/`merge --ff-only` path that actually produces the sentinel. A verifier of a self-healing/restart mechanism must rebuild the real triggering path independently, not just re-run the reaction-side probes and call the consumer condition proven.

2. **Independently re-deriving a risk the builder already disclosed is corroboration, not a new discovery, and must be reported as such.** When this session's own adversarial TOCTOU stress test confirmed the exec-guard race the PR's own record had already named as an accepted, un-eliminated residual, the correct framing was "this session's own number corroborates what's already disclosed," not "gotcha, the PR hid this" — conflating the two would misrepresent an honest builder disclosure as a missed defect.

3. **Grading a builder's honest hedge ("open finding" rather than an assumed claim) is itself part of the verification task, not something the hedge exempts from scrutiny.** "Judge whether that honesty is warranted or whether it was closable with available means." An open finding is not automatically Present just because it's disclosed rather than asserted — the verifier still has to check whether more of the gap was closable with available, no-risk means (here: process start-time invariance under `exec()`, derivable from POSIX semantics without touching any live process) before accepting the hedge as the correct stopping point.
