canonical: this session's own spawning prompt (2026-09-02), read this session.

The spawner stated principles specific to combining two already-verified,
disjoint-file PRs into one landable delivery when an issue's acceptance
checks are split across them by pure sequencing (not a defect in either
side):

1. **A split acceptance section across file-disjoint PRs is a sequencing
   problem, not a defect in either PR** — each PR scoring short on the
   other's probes does not mean either PR is wrong; it means the two need
   combining before either can land. The combining session must not treat
   either PR's own probes/code as suspect just because `merge_gate` refuses
   both individually.

2. **"Take both sides" is the default conflict-resolution stance for two
   independently-verified deliverables, reserved for structural
   overlap (both sides registered something at the same doc location) —
   but a semantic choice (two sides disagreeing about what the *content*
   should be, not just where it's placed) must stop and get recorded
   rather than picked** by the combining session alone.

3. **An open question raised independently by two separate verification
   passes is worth a live check, not just a repeat of prior reasoning** —
   the spawner named a specific interaction (exec self-heal vs. wake-notice
   staleness) that "both are still running" verifications had flagged but
   not resolved; the combining session, having both codebases in one tree
   for the first time, was asked to actually observe it rather than defer
   the question again.

4. **Closing the other, now-subsumed PR is explicitly the orchestrator's
   job, not the combining session's** — so verification records already
   attached to that PR/issue stay attached rather than getting scattered by
   a premature close from inside a build session.
