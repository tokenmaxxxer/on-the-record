The spawning prompt stated several standing principles while scoping round-2 test additions to `scripts/preflight/consumer_preconditions.py` and `docs/handbooks/install-sufficiency.md`:

1. **A test must fail for a real reason before it can be trusted, and that must be demonstrated, not asserted.** "Make the tests fail for a real reason if the deliverable regresses: confirm this by temporarily breaking one behavior, watching the test fail, and restoring it. Record that transcript." Applied this session across three separate assertions (a bad `source` citation, a flipped `remote_push_access` boolean, and a renamed doc heading/phrase) rather than trusting a single case to stand in for the whole file.
2. **A safety/read-only property claimed only in a PR description's prose is not verified — it must be re-run as a repeatable assertion.** The read-only claim ("never mutates the machine") from PR #3184's own description was re-tested by running the preflight twice and diffing `git status --porcelain`, rather than accepted on the strength of the original PR's own test-plan note.
3. **Portability must hold identically across macOS and Linux with no GNU-only flags and no `/proc` reads**, stated explicitly as a constraint on any new script/test touching this preflight, even though this session had no macOS runner to verify it live on (a residual limitation logged in the record rather than silently assumed clean).
4. **Round-2 continuation work on an open PR is pushed directly onto that PR's own branch, not delivered as a competing new PR** — when a task explicitly names an existing PR as the landing target, the spawned session's own branch/PR carries only its record, not a duplicate of the code.
