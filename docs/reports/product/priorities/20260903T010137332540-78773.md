# Priority: an enforcement hook that always declines is worse than no hook

Stated this session (round 3 on PR #3232, the delegation Stop hook): a
gate/hook that runs on every turn but can never actually fire (e.g. every
return path hardcoded to the non-suppressing/non-blocking outcome) is
worse than either removing it or turning it into an after-the-fact
reporter — it still costs latency and still reads as protection while
providing none. Round 2's fix to a real over-refusal defect
over-corrected into exactly this state (`_live_stop_decision_body()`'s
nine return sites all hardcoded `suppress: False`), and the standing
instruction was: if the design genuinely cannot distinguish the two cases
a live enforcement hook needs to tell apart, say so explicitly and
recommend downgrading the hook's role — do not ship the always-declining
version silently.

**Applies to:** any future round on this hook, and by extension any other
live enforcement hook in this repo (Stop hooks, pre-commit gates,
delegation checkers) where a defensive fix is tempting to over-apply into
a permanent no-op.
