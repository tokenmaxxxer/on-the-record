The operator stated a standing design principle across two corrections on issue #2904, escalating each time observation was found too coarse: **a check's clean output must never be indistinguishable from "nobody looked."** Concretely, in priority order as stated:

1. Notification is not enough — the orchestrator "spawned these sessions itself" and must actively track them (pid, workspace, branch, issue), not wait to be told. An orchestrator that must remember to check will forget ("it forgot three times in one night").
2. `gh`-based checks are late by construction (only see a session after a PR/comment exists) and burn API budget — local, already-running machinery (git status, the session's own transcript log) must be preferred over polling GitHub.
3. File-diff state is still too coarse: "file changes are the *result*; tool calls are the *act*, and only the act says what is happening." A check must be able to tell *investigating* from *stalled* from *stuck-in-a-loop*, not collapse all of them into "no change."
4. Any such mechanism must hold structurally for every session on every on-the-record install, without a per-session or per-orchestrator opt-in, and must not add per-turn instruction overhead, general heartbeat volume, or a `gh` polling loop, and must never trade away an existing anomaly signal to add a new one.

This is stated as the fourth occurrence of the same defect shape in one night (prior instances: #2876 plural handling, #2873 uncollected test directories, #2889 unanchored cwd) — the operator treats this as a recurring category of bug worth naming and checking for explicitly in future work, not a one-off.
