## Where the record-format contract actually lives today

Three checks fire on `docs/issue-*/reports/**` writes, in two different
repos:

- `gates/record_lint.py` + `on-the-record/hooks/record-claim-guard.sh`
  (PreToolUse, **this repo**, applies to every role via the shared plugin):
  denies a bare `N of M`/`N items` count with no `derived:` citation or
  code-fence reproduction (`record_lint.py:66,100-119`).
- `on-the-record/hooks/accumulation-claim-guard.sh` (PreToolUse, **this
  repo**, shared): denies specific accumulation shapes (≥3 inline
  subprocess/`gh` call sites, or `roles/*.json`-style repeated one-line-edit
  files) unless the local proposal carries a filled `## Accumulation`
  section.
- `record-fields-gate.sh` — the check the issue names for the `code_
  under_review` bare-sha symptom — does **not exist live in this repo**.
  The only copy found anywhere is a frozen template snapshot,
  `docs/issue-170/_assets/rulebook-skeleton/<role>/<role>/hooks/
  record-fields-gate.sh`, whose own header says "adapted per issue-170 from
  `roles/<role>.json`'s `produces`... Skeleton: field-presence checks are a
  placeholder (substring/heading match) — harden before treating as
  load-bearing." The live version each role actually runs is a per-role
  copy inside that role's own **external** rulebook repo (e.g.
  `tokenmaxxxer/architecture-rulebook`, confirmed present as a separate git
  checkout under `/tmp/claude-*/.../architecture-rulebook` in this
  environment) — not a path this on-the-record checkout can read or write.
  That copy checks required field **names** are present as substrings; it
  never asserts that `code_under_review` is a YAML list of paths rather
  than a bare commit sha, so a session that writes a sha passes that gate
  and gets caught only by whatever else reads `code_under_review`
  downstream.

## Where the correct shape already IS documented/generated (this repo)

- `on-the-record/hooks/record-scaffold.sh` (CLI, this repo, issue #517):
  `record-scaffold.sh <role> <issue-n>` writes a skeleton record with
  `code_under_review:\n  - PLACEHOLDER: path/to/file` — already the correct
  list shape — plus one `PLACEHOLDER: <field>` line per
  `roles/<role>.json`'s `record_fields`. `record_lint` then flags any
  surviving placeholder.
- `docs/handbooks/record-authoring.md` (this repo, issue #517) documents
  both `record_lint` and `record-scaffold.sh` and is the only place the two
  are described together as a "run before/after authoring" pair.
- Neither is invoked automatically. `record-scaffold.sh` is CLI-only by
  design (its own header: "nothing in the write path fires 'author is about
  to start a record,' so there is no lifecycle event to register it against
  in `hooks.json`" — a prior warrant-hunter finding on #517 already ruled
  out a PreToolUse form). A session only runs it, or reads
  `record-authoring.md`, if something tells it to.

## Why the authorship point never sees the contract

The text actually injected into a role session at `SessionStart` — what
this very session saw as `[architecture] Role directive` — is generated by
`hooks/directive.sh` inside that role's **own external rulebook repo**, not
by anything in on-the-record. Confirmed by diffing the injected text
against the frozen skeleton at `docs/issue-170/_assets/rulebook-skeleton/
architecture/architecture/hooks/directive.sh`: the live version this
session received already carries an extra sentence pointing at
`docs/handbooks/architecture-methodology.md` and
`arch-phase1-checklist/agents/phase1-checklist.md` that the frozen skeleton
snapshot does not have — i.e. someone has already edited the live external
`architecture-rulebook` directive text at least once since issue-170, using
exactly this "point the directive at an on-the-record handbook" pattern.
That precedent exists; it has just never been applied to record-authoring.
Neither the frozen skeleton nor (by inspection of the live text) the
external directive.sh's `RECORD:` line mentions `record_lint`,
`record-scaffold.sh`, or `docs/handbooks/record-authoring.md` at all — the
session is told *where* its record goes and *which fields are required*,
never *how to shape them* or that a generator/linter exists.

The `[core] Interaction protocol` text (the role-handoff contract v3
prose) is not sourced from this repo either — no match for its literal
strings anywhere in this checkout outside one survey file quoting it. It
too lives in an external repo.

## Gap this issue must close

The mechanical shape contract (list-typed `code_under_review`, `derived:`-
cited counts, filled `## Accumulation`) is split across:
1. two enforcement points this repo owns and that already fire for every
   role (`record-claim-guard.sh`, `accumulation-claim-guard.sh`), plus
2. a third enforcement point (`code_under_review` shape) that has **no
   live check anywhere** — only a placeholder-quality per-role substring
   gate in each external rulebook repo, and
3. a generator/handbook pair this repo owns (`record-scaffold.sh`,
   `record-authoring.md`) that is correct but silent — nothing surfaces it
   at the moment a session starts authoring.

None of (1)-(3) is reachable from the `SessionStart` text a session
actually reads before writing its first record byte, because that text is
authored in per-role external repos this on-the-record checkout cannot
write to. A fix confined to on-the-record cannot edit those ~13+ external
`directive.sh` files directly.
