# Per-mounted-skill verdict obligation in role records

## Request

For every skill named in a spawn directive's mounted-skill list, the role record must carry one `skill-verdict: <name> — applied: <where/how> | not-applicable: <one-line reason>` line. Enforcement is a record-fields/record-shape shape check only (never interpreting the skill's own content) — this closes the gap where a session can ignore every mounted skill with zero consequence, without ever having to state a position.

## Constraints

- Shape check only: the gate verifies N `skill-verdict:` lines exist, one per mounted skill name, each with non-empty content after the dash. It must never parse or judge whether the stated "applied"/"not-applicable" content is actually correct — that stays the session's own judgment, per the frozen skills-guidance-only principle (spawn.py:8181's own `가이던스만 붙는다 — 집행은 core 훅뿐이다` line already states this boundary for skill content generally).
- A session with zero mounted skills must be byte-unaffected: no new record requirement, no new hook output, nothing added to the record contract.
- The spawn directive must state the obligation next to the mounted-skill list (spawn.py:8143-8196), on top of — not instead of — the existing #1960 스킬 점검 nudge.
- Enforcement has to work for both mounted-skill assembly points identified in the survey (`--skills` at spawn.py:8151 and the role→skill-repository mapping at spawn.py:8179), and for a session that carries both at once, without double-counting a skill that appears in both lines.
- Hook tests must cover: missing skill-verdict line, empty-reason skill-verdict line, and zero-mounted-skills (no-op).

## Rationale

The survey's central finding is that the mounted-skill list only ever exists in the spawned session's own transcript — never in a file the target repo's git tree or CI can read independently. That forces a choice between two designs:

**Chosen: session-side Stop hook, transcript-scan mechanism (mirrors `deviation-log-guard.sh`).** A new `skill-verdict-guard.sh` reads `transcript_path` off the Stop event JSON, scans the JSONL transcript for the first-user-message mounted-skill line(s) (spawn.py:8151/8179's exact prefixes), extracts the skill name set, and cross-checks the changed record's diff for a matching `skill-verdict:` line per name — refusing via `additionalContext` (not `decision:"block"`) exactly as `deviation-log-guard.sh` and `product-capture-stopgate.sh` already do for their own shape checks.

**Rejected: persist the mounted-skill list into a committed manifest (e.g. record frontmatter field written by spawn.py, or a sibling `docs/issue-<n>/.mounted-skills.json`), then enforce purely as a CI-side `gates.py` function reading that manifest plus the record.** Rejected because it requires spawn.py to write into the target repo's working tree at spawn time, before the session has done anything — a new write surface with its own staleness/tampering questions (a session could edit or delete the manifest same as any other file, whereas the transcript is generated by the harness outside the session's write access) and a new commit-shape requirement (the manifest would need its own trailer/lint treatment to land safely). The transcript-scan approach reuses an existing, already-hardened pattern (two live hooks already do exactly this) and needs no new persisted artifact, at the cost of being session-hook-only rather than also CI-diff-enforceable on a PR days later. Given the empty-state evidence in the issue (cycle-2 sessions producing zero skill positions) is itself a session-time behavior gap, a session-time hook closing it directly is the correct level, and a CI-side companion function can be added later without contradicting this choice if manifest-based enforcement is ever wanted.

## What will be done

1. **`spawn.py`** — immediately after the existing #1960 스킬 점검 nudge (spawn.py:8191-8196), when either mounted-skill block fired, append one line stating the verdict obligation next to the mounted list: naming the `skill-verdict: <name> — applied: ... | not-applicable: ...` line shape and that it is required once per mounted skill before the record can be written. No output changes when neither block fired (byte-identical, per Constraints).
2. **`gates/record_lint.py`** (canonical check) — add a `record_skill_verdicts_in(work, mounted: list[str])`-shaped check alongside the existing lifted checks, following `record_lint.py`'s existing pattern of one function per rule, callable from both `gates/ci.py` and the new hook. Since CI has no transcript, this canonical function takes the mounted-skill names as an explicit argument rather than discovering them itself — the hook is the only caller that derives that argument from a transcript scan; a future CI caller would need its own source for the argument (out of scope here).
3. **`on-the-record/hooks/skill-verdict-guard.sh`** (new Stop hook) — mirrors `deviation-log-guard.sh`'s shape: read the Stop event JSON, extract `transcript_path`, scan the transcript's first user message for the two known mounted-skill line prefixes (`마운트된 스킬(--skills` and `이 역할은 skill-repository(`), parse skill names out of each (comma-split, strip trigger/source parenthetical suffixes), union the two sets, then check via `git diff`/`git log -p` on the changed record path whether N matching `skill-verdict:` lines landed (delegating the actual line-shape check to `record_skill_verdicts_in`). Zero mounted skills → exit 0 immediately, no output. Same fail-closed trap / `ORCHESTRATE_OFF` kill switch as its sibling hooks.
4. **Tests** — `on-the-record/hooks/test_skill_verdict_guard.py` covering missing-line, empty-reason, and zero-skill paths per Acceptance; `gates/test_record_lint.py` gains cases for the new canonical function.
5. **`docs/handbooks/skill-verdict-obligation.md`** — short handbook entry stating the obligation and line shape, referenced from the hook's refusal message, matching the convention `deviation-log-guard.sh` uses (its refusal message points at `docs/handbooks/deviation-loop.md`).

## Accumulation

This adds one new hook (`skill-verdict-guard.sh`) and one new canonical check function, not a per-role repeated edit — `roles/*.json` itself is untouched (Out of scope). If N more issues each add their own Stop hook mirroring `deviation-log-guard.sh`'s transcript-scan shape, `on-the-record/hooks/` grows by one file and one paired test per issue, same as its existing sibling hooks today — that is the established pattern for this directory, not a new accumulation risk this issue introduces. The one place true accumulation could occur is the transcript-scan line-prefix list inside `skill-verdict-guard.sh` (currently two prefixes, matching spawn.py's two assembly points) — if spawn.py ever grows a third mounted-skill assembly point, that hook's prefix list needs one more entry; this is a single well-known extension point, not an unbounded list.

## Out of scope

- Judging whether a stated "applied"/"not-applicable" reason is actually true or well-reasoned — shape-only, per Constraints.
- A CI-side (`gates.py`) enforcement path that doesn't depend on a session-hook transcript scan — the Rationale names this as a possible later addition, not this issue's delivery.
- Retroactively adding `skill-verdict:` lines to any existing record.
- Changing the `roles/*.json` `record_fields` schema — the per-spawn mounted-skill count doesn't fit a per-role enum declaration (survey finding), so this stays outside that mechanism entirely.

## How you'll know it worked

- A record write for a session whose transcript names N mounted skills is refused by `skill-verdict-guard.sh` unless N `skill-verdict:` lines are present, one per mounted name, each with content after the dash — verified by the three hook test cases (missing line, empty reason, zero-skill no-op).
- A session with zero mounted skills produces no hook output and the record is byte-unaffected — covered by the zero-skill test case.
- The spawn directive text (spawn.py) states the obligation next to the mounted-skill list, verified by a spawn.py-side test asserting the new line's presence when skills are mounted and its absence when none are.
