# ADR: harden pr-preflight's Closes-trailer refusal (issue #653)

## Context
Phase-2 delivering PRs must carry `Closes #<n>`. `pr-preflight.sh` already
denies at `gh pr create`/`edit` time when this is missing, but its own
phase-2 detection is not round-scoped the way #577 fixed
`contract-guard.sh`'s detection to be, and it reads `--body-file` content
before the underlying command has written that file — either gap can let a
bad phase-2 PR body through preflight uncaught, so the omission is only
caught later by `contract-guard.sh` at merge time, forcing the
body-edit-then-merge workaround the issue reports. See
[survey.md](../reports/architecture/survey.md) for the code-level detail.

Claude Code `PreToolUse` hooks in this deployment only ever return
`allow`/`deny` (+ reason) for `Bash`; no hook here rewrites the intercepted
command. Auto-attaching the trailer into a `gh pr create` invocation before
it runs is therefore not available on this deployed surface without adding a
command-rewrite capability nothing else in this hook set uses — out of
proportion to a zero-install, no-Actions fix. Ruled out; see survey §"Why
auto-attach is not viable."

## Decision
Harden the existing pre-create refusal instead of adding auto-attach:

1. **Compose #577's round-scoped signal into `pr-preflight.sh`.** Extract
   the `first_commit_at`-gated phase-2 determination
   (`contract-guard.sh:119-165`) into one shared computation both hooks call,
   rather than pr-preflight keeping its own unscoped copy. Concretely: factor
   the shared logic (approvers.md read, comment scan, round-scoping) into a
   small inline Python function duplicated verbatim in both scripts (these
   are zero-install hooks with no shared importable module today — see
   `contract-guard.sh`'s own header rationale for why they port logic inline
   rather than import `gates/`). Duplication is deliberate and matches the
   existing pattern; the fix is that both copies implement the *same*
   round-scoping, not that a new import path gets invented.
   - `pr-preflight.sh` has no PR yet at `create` time, so it has no
     `pr view --json commits` to read. Its round anchor instead becomes the
     **current branch's own first commit** (`git log --reverse --format=%cI
     <merge-base>..HEAD` against the branch's fork point, or simplest: the
     earliest commit reachable from HEAD not on the issue's default branch).
     Any APPROVE comment older than that commit belongs to a prior round and
     must not force phase-2 on this branch's PR.
2. **Fix the body-file race.** For `--body-file`, if the referenced path
   does not exist at hook-check time, do not silently fail open. Fail open
   only stays correct when the omission is genuinely unreachable (per the
   script's own fail-open policy comment); a file that will be created by an
   earlier `&&`-chained command in the *same* Bash invocation is a knowable,
   checkable case. Preflight already has the full command string (`cmd`) —
   extract and evaluate the body-producing prefix (`printf ...>`, heredoc
   `cat <<EOF > path`) inline the same way it already ports `check_body`, so
   the trailer check runs against the content that will land in that file,
   not against nothing.

## Consequences
- Both hooks converge on identical phase-2/round-scoping semantics; a future
  fix to the signal (e.g. #577-class bugs) is made in both places by the
  same reasoning, not independently rediscovered.
- The pre-create refusal actually fires on the `--body-file` pattern that
  today silently passes through, closing the gap that let the omission reach
  merge time repeatedly.
- No new install/CI dependency; both hooks remain zero-install, `gh`+
  `python3` only.
- Residual risk: a `gh pr create` invoked with body content generated by a
  command this hook cannot statically evaluate (e.g. body piped from a
  network call) still fails open, same as today — documented as a known
  limit, not solved by this issue.

## Alternatives considered
- **Auto-attach via command rewrite.** Rejected: no hook in this deployment
  rewrites `Bash` tool input; building that capability is a materially larger
  surface (arbitrary shell/heredoc reparsing) than hardening the refusal
  that already exists, for a zero-install/no-Actions constraint.
- **Auto-attach via a wrapper script the role is told to call instead of
  `gh pr create` directly.** Rejected: this reintroduces exactly the
  task-prompt-instruction-leak problem #653 exists to eliminate — depends on
  model compliance to invoke the wrapper instead of `gh` directly.
- **Move the check to CI (GitHub Actions) instead of a local hook.** Rejected
  by the issue's own constraint (zero-install, no Actions) and because it
  moves the refusal from pre-create (cheap, no PR created) to post-create
  (a PR now exists and must be edited or closed).

## C4 (context/boundary)
```
[Role session (Claude Code, this repo)]
        | Bash: gh pr create --body ...
        v
[PreToolUse hook chain]
   contract-guard.sh  (gh pr merge)  -- existing round-scoped phase2 signal
   pr-preflight.sh    (gh pr create/edit) -- phase2 signal to be aligned here
        |
        v  allow / deny(reason)
[gh CLI] --(if allowed)--> [GitHub PR]
```
Boundary: this issue only touches the `pr-preflight.sh` hook's phase2
determination and body-file read; it does not change `contract-guard.sh`'s
existing (already-correct) logic, and does not add any new hook, script, or
CI job.

## Hand-off
Interface/CLI-flag shape of any factored-out shared function stays inside
`on-the-record/hooks/` — no `api-design` hand-off needed. No performance
budget is at stake (single `gh` call latency, unchanged) — no
`performance-engineering` hand-off needed. Implementation (phase 2, after
approval) stays within this same architecture role's branch per contract
v3 s19.
