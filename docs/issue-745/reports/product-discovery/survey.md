# Survey — issue #745: session cost-structure valuation

## Background / context

This repo ("on-the-record") runs Claude Code agent sessions under structured roles (`product-discovery`, `implementation`, `architecture`, `execution-observation`, ...), each gated by `gates/*.py` and hooks before a PR lands. Every session is logged to a ledger (`runs/ledger.jsonl`, resolved on this machine at `/Users/jk/.claude/plugins/marketplaces/tokenmaxxxer/runs/ledger.jsonl`, gitignored) plus a per-session stream-json log file referenced by the ledger row's `log` field — the same data source `docs/issue-501/proposals/2026-08-08-session-latency-breakdown.md` already used to establish that model working time dominates wall-clock over fixed startup (86.3% on that day's earlier sample, method: sum each session's own log `duration_api_ms` over ledger `duration_s`), and that no per-event timestamp exists except the session's final `result` line.

Issue #745 cites a follow-up "2026-08-11 성능 분석" of 219 sessions, 48.6 hours, and $880, decomposing *within* that dominant model-time term for the first time: how much of it is extended thinking, how much is record/documentation output, and how much belongs to the `execution-observation` role specifically (whose evidence the issue says produces zero code output on a third of that spend). This analysis was not found committed anywhere in `docs/` (searched for "219", "48.6", "880", "성능 분석", "98.1%" — no hits), so this survey re-derives it directly from the live ledger, below, rather than treating the issue's numbers as unverifiable priors.

The issue explicitly frames all three items as **designed costs, not defects** — thinking buys judgment quality, records buy auditability, `execution-observation` buys the self-report trust floor `docs/issue-476/decisions/2026-08-08-h1-h2-mechanism-adr.md` established — and explicitly defers any cut decision to the operator (see the issue's own "결정 유보" section). This survey and the accompanying proposal stop at valuation and pre-registered alternatives; no execution role is assigned past `step 1 product-discovery` in the issue's own 실행 계획.

## Problem, stated without solution (JTBD)

The issue names candidate directions in passing (env-var thinking tuning, condition-gated `execution-observation`) but its own "조사가 답해야 할 것" section frames the ask as open investigation, not a chosen fix — restated in the customer's terms, before any mechanism is picked:

- **Job performer**: the operator who authorizes and pays for role-session spend across this repo's issues, deciding per-issue and per-role where budget goes.
- **Job**: know, for each of three cost centers (thinking, records, execution-observation), what it is buying and at what price, so that a cut decision — if one is ever made — targets a measured overpayment instead of a guess, and a kept cost is kept because a metric showed it earns its keep, not by default inertia.
- **Circumstance**: model generation dominates session wall-clock (re-derived below), thinking and record output together already account for more than half of that generation's output tokens, and the repo has accumulated a large body of its own report and proposal files with no existing measurement of which of them ever get read again. No pre-registered metric exists yet for any of the three items — cutting today would be exactly the "no threshold ever fixed" failure this role's own methodology exists to prevent.
- **Desired outcome**: for each cost center, a stated current spend traceable to a real command against real data, one or more reduction candidates scored against that spend, and — for each candidate — a named metric, a numeric threshold, a guardrail, and a revert condition, fixed before any of them is ever tried.

## Where this sits on the opportunity-solution tree

- **Outcome**: this repo's per-issue session cost is spent on judgment quality, auditability, and self-report trust at a price the operator can see and audit — not spend that is either cut blindly or left unexamined by default.
- **Opportunity**: no existing mechanism separates "spend that bought the named good" from "spend that didn't," for any of the three cost centers — the same self-report-trust gap `#476` closed for code-execution claims (mechanized re-execution, never a re-read of prose — see below) has never been pointed at the repo's own resource spend.
- **Candidate solutions**: per-role thinking-effort conditioning; citation-informed record-section tiering; diff-size/revert-difficulty/claim-type-conditioned `execution-observation` spawning. Scored in the accompanying proposal.
- **Discriminating assumption test**: whether a measurable, pre-registered metric can tell "this spend bought the named good" from "this spend was pure overhead" for each item, without breaking the good the spend exists to buy — this is what a follow-up measurement round would answer, if the operator approves one; not assumed true here.

## What the repo actually does today (checked, not assumed)

### 1. Thinking budget

Sorting `runs/ledger.jsonl`'s 222 dated session rows by `ts` and taking the first 219 reproduces the issue's cited figures almost exactly: `derived: sort ledger rows by ts ascending, take first 219, sum duration_s and cost_usd` — duration_s sum 174,924s (48.59h), cost_usd sum $880.05, against the issue's cited 219 sessions, 48.6 hours, $880. No field-based filter (date/repo/role/outcome) reproduces the same set; it is a chronological snapshot taken mid-day 2026-08-11, before 3 more sessions landed. The full current ledger (222 rows) sums to 49.76 hours and $899.00 — about 2% higher, consistent with organic growth since the snapshot.

Joining each of the 219 snapshot rows' own log file's `{"type":"result"}` event `duration_api_ms` against the ledger's `duration_s`, for the rows whose log file still exists on disk (153 `derived: count of the 219 snapshot rows whose ledger "log" path still exists on disk` of the 219), gives model-generation share of wall-clock: 116,570.1s of model time over 119,885.7s of wall-clock for that subset, **97.23%** (issue cites 98.1%; issue-501's prior day measured 86.3% on a different sample — day-to-day drift is expected, both far above zero).

This repo's session logs carry a `{"type":"system","subtype":"thinking_tokens","estimated_tokens":N,"estimated_tokens_delta":D}` event per turn, where `estimated_tokens` resets roughly every turn and only `estimated_tokens_delta` sums correctly across a session. `derived: sum estimated_tokens_delta per session, divide by the session's own result-event usage.output_tokens, across the 152 snapshot sessions carrying both fields` — thinking is **49.26% of output tokens (sum-weighted across those sessions), 44.98% (median per-session)** — inside the issue's cited 40-51%. Caveat: `estimated_tokens` is a client-side estimate; the Anthropic API's own `usage` object carries no thinking/text/tool_use token split at all.

No per-role or per-session thinking-budget configuration exists anywhere in this repo today: `derived: grep -rn "budget_tokens\|thinking_budget\|effort" roles/*.json spawn.py` returns no matches. Whether the model this harness actually invokes even accepts a manual thinking-budget parameter is unconfirmed by anything in this repo — see `scout-brief.md`'s caveat that newer Claude models reportedly reject a manual `budget_tokens` in favor of adaptive thinking.

### 2. Record output ("기록물")

Across 77 sampled `implementation`-role sessions with retrievable logs, `derived: count Write/Edit tool_use calls per session, classify target path by extension, .md vs code` — `Write` calls numbered 302, with 187 targeting `.md` (61.9%); `Edit` calls numbered 327, with 133 targeting `.md` (40.7%); combined, 50.9% of Write-plus-Edit calls target markdown. A token-share proxy (Write `content` field character length divided by 4) puts markdown content at 9.0% of *total* output tokens, or **22.2% of non-thinking output tokens** — inside the issue's cited 17-24% range if that range's denominator excludes thinking output, as this survey's own thinking-share finding above suggests it should. The single most lopsided session found, `on-the-record-issue-246-implementation` (762.7s, $3.26, all 18 of its Write-plus-Edit calls targeting `.md` `derived: same per-session Write/Edit extension classification, filtered to sessions with at least 10 calls`), hit 100% markdown — not the issue's cited 91%. The qualitative claim ("one implementation session, almost all Write calls markdown") holds; the specific 91% figure does not reproduce in this sample and may belong to a session outside it or to a different counting method.

Repo-wide inventory finds a total record/proposal population of 1,070 files: `derived: find docs -type f -name "*.md" | grep -E "docs/(issue-[0-9]+/(reports|proposals)|reports)/" | wc -l`. A path-fragment citation script (does file A's path appear inside any other file B's body, excluding self-matches, with a boundary guard against parent/child path prefix collisions) finds cited-at-least-once and never-cited counts of 758 and 312 `derived: repo-wide path-fragment cross-reference script over the 1,070-file inventory, each file's stripped path searched against every other file's body` respectively out of the 1,070 total — 70.8% cited, 29.2% never cited. By category, cited rates run from a high of 93.8% for `proposals/*.md` down to a low of 56.1% for `reports/<role>/survey.md`, with `reports/<role>.md` at 64.1%, repo-wide `docs/reports/*.md` hunt files at 65.8%, `scout-brief*.md` at 62.3%, issue-scoped `hunt-*.md` at 66.7%, and `current-state*.md` at 75.0%.

Of files that *are* cited, the citation itself is disproportionately same-issue-only for phase-1 research artifacts and disproportionately cross-issue for the artifacts meant to persist: `survey.md` citations are same-issue-only 73.8% of the time (read once by the same issue's next phase, then never again), `scout-brief*.md` same-issue-only 90.7%, issue-scoped `hunt-*.md` same-issue-only 100%. By contrast, repo-wide `docs/reports/*.md` hunt files are cross-issue 98.7% of the time, `reports/<role>.md` 67.7%, proposals 56.9% — proposals and final role reports function as institutional memory; phase-1 survey and scout-brief artifacts function as disposable scratch that is read once and dies. What gets cited is consistently a named decision, verdict, table, or root-cause finding referenced by section-header name or quoted claim — for example `docs/issue-609/proposals/architecture.md` citing "product-discovery's RICE table (candidate 1)" by name — never boilerplate: the standard `## What did not work` section appears 227 times across reports repo-wide, and is quoted or referenced from any other file in exactly zero of those instances `derived: grep -c "^## What did not work" across docs/issue-*/reports, cross-checked against the citation script's per-file citer list for any hit whose citing snippet quotes that section`.

Among uncited files, 94 are at least 8 days old, each with a median of 912 later record files written after them (minimum 757, maximum 969) `derived: for each uncited file, count other record/proposal files with a later add-date via git log --diff-filter=A --name-only` — hundreds of subsequent sessions had the opportunity to cite them and did not. The repo's history is short (2026-07-27 through 2026-08-11), so a true "over two weeks old, never cited" bucket cannot yet be measured cleanly; this is the best available proxy for "genuinely unread" rather than "hasn't had a chance yet."

### 3. `execution-observation`

Within the 219-session snapshot, role-value counts run implementation 127, execution-observation 76, conformance-review 11, test-authoring 3, refactoring-legacy 1, product-discovery 1 `derived: value_counts of the ledger "role" field over the 219-session snapshot`. `execution-observation` accounts for 76 of those 219 sessions (34.7%, issue cites 35%), 27.6% of duration, and $291.98 of the $880.05 total cost (33.18%, issue cites "33% of cost"). The single most expensive `execution-observation` session by duration is `tokenmaxxxer-core-issue-106-execution-observation` at 1693.2s/$11.91 — larger than the issue's cited example. A near-exact match to the issue's cited "863s/$4.51" example exists at `tokenmaxxxer-core-issue-157-execution-observation`, session `37e1a6ce…`, 869.7s and $4.5064.

Of the 282 Write-plus-Edit calls across the 62 `execution-observation` sessions with retrievable logs, 268 target `.md` files (95.0% `derived: same per-session Write/Edit extension classification as the record-output section, filtered to role=execution-observation`); the remaining 14 are scratch scripts outside the repo tree or commit-message text, not committed repository code — supporting the issue's "zero code output" characterization for this role.

`#476`'s self-report-trust-ban mechanism is **mechanized independent re-execution, not sampling and not an LLM-verifier subagent**: `gates/claim_scan.py` regex-matches claim vocabulary and hard-fails a record lacking an adjacent reproducible command; `gates/reexecution_gate.py` then re-runs that exact command inside a fresh, detached `git worktree` at the head SHA — never the audited session's own checkout — and writes a result file the audited role cannot write to. `docs/issue-476/decisions/2026-08-08-h1-h2-mechanism-adr.md` ("Decision → H1") explicitly rejected an "LLM-verifier subagent reads the record" alternative as "still self-report shaped from the ground-truth side." As of `docs/issue-476/reports/execution-observation.md`'s 2026-08-10 update, the mechanism existed but was not yet auto-wired to fire (`fabrication_survival_rate` measured undefined/unwired); `docs/issue-476/proposals/discovery-round2.md`'s candidate A fixed this with a `PreToolUse` hook on `gh pr create`/`gh pr edit`, now live at `on-the-record/hooks/claim-scan-preflight.sh` (registered in `on-the-record/hooks/hooks.json`).

`execution-observation` spawning is **conditioned on paper, not enforced in practice**: `roles/execution-observation.json`'s `use_when` field states a `board_condition` — an executable artifact landed on the branch and no execution-observation record exists yet for this commit sha — but `spawn.py`'s `drive()` (citing issue #120 in its own docstring) explicitly leaves "who to spawn next" to orchestrator judgment, not a machine-evaluated routing table; no landing/closure gate requires an `execution-observation` record before merge. Empirically this already produces sparse, not universal, coverage: `derived: count directories under docs/issue-*/ containing an implementation.md report vs any execution-observation*.md report` — 158 issue directories carry an `implementation.md` report, and only 25 of those carry any `execution-observation*` record at all, meaning 133 implemented issues (84%) have no `execution-observation` record. The issue text's own "이슈당 구현 2세션 + 관찰 2세션" framing describes the sessions that *do* spawn it, not a claim that every issue gets it.

An existing, already-normalized precedent for conditioning a verification-shaped role by artifact type — not sampling, a full skip — is warrant-directive's own "docs-only fast path": when every touched path in a transition is under `docs/`, the before-landing hunter dispatch is skipped outright, cited across multiple hunt records including `docs/reports/2026-08-08-hunt-per-row-delivery-and-batch-split.md` and `docs/reports/2026-08-08-hunt-architecture.md`. This is a live analogue for conditioning `execution-observation` similarly: the trust ban targets *unverified execution claims*, and a diff with nothing executable makes independent re-execution vacuous by the same logic `roles/execution-observation.json`'s own `board_condition` already states.

## Scout-informed gap (see `scout-brief.md`)

Current state meets none of the three literatures' must-bes on the primary role-session surface — no thinking-budget knob exists (confirmed above), no record retention or tiering policy exists (only an unused citation signal, measured above for the first time), and `execution-observation` conditioning exists as unenforced orchestrator judgment rather than a measured rule. What is missing, and becomes this proposal's discriminating axis: a named, pre-registered metric for each item that would show whether trimming it degrades the specific good it buys — judgment quality, auditability, self-report trust — before any trim is ever tried. Not whether it saves tokens, which every number above already shows it does.
