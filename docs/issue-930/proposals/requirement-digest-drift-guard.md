# Proposal — requirement digest & drift guard (issue #930)

## Candidate comparison (RICE)

| Candidate | Reach | Impact | Confidence | Effort | RICE (R*I*C/E) |
|---|---|---|---|---|---|
| A. New derived digest (spec_index.py-pattern) + drift check added to the existing advisory sweep (accumulation_trend()-pattern) | every installed session, any repo size (10) | closes req#6's actual gap: O(requirement-count) digest + standing drift signal (9) | high — both underlying patterns already ship and are proven (8) | medium — one new gate module, one new hook, one sweep addition (4) | 162 |
| B. Fold digest content into `requirements.md` itself, no separate drift check | same reach (10) | partial — meets "condensed" but not "drift guard" half of req#6 (4) | high, smallest surface (8) | small (2) | 128 |
| C. Digest computed by scanning the full `docs/issue-*/reports/` tree each run | same reach (10) | richer per-issue detail, but reintroduces O(record-count) cost — the exact drift #930 names as the failure mode (5) | medium — feasible but slower as records grow, and duplicates each issue's own record (5) | large — new tree-walk + per-record parsing (7) | 18 |

Evidence for scores: survey's OST section and gap line — candidate A
reuses two already-shipped, already-proven mechanism families
(`gates/spec_index.py` + `on-the-record/hooks/spec-index-preflight.sh`;
`accumulation_trend()` inside `spawn.py`'s `_board_wide_sweep()`),
which is why Confidence and Effort both favor it over C. Candidate B
is rejected on Impact: it satisfies "condensed" but drops the standing
drift-guard half of the requirement outright, which the issue's
acceptance section requires as a distinct harness assertion. Candidate
C is rejected on Effort/Impact: re-deriving from the full record tree
each run is the O(record-count) shape the survey's discriminating
assumption test specifically warns against. Candidate A is carried
forward.

## What will be done (design, no code beyond gate/hook wiring)

**1. The digest artifact — `docs/specs/requirement-digest.md`.**
Derived, not hand-authored: one condensed line per entry currently in
`docs/specs/requirements.md`, in registry order —
`- R###: <paraphrase, truncated to ~120 chars> [status] (source: #<issue>)`.
Generated by a new `gates/requirement_digest.py`, mirroring
`gates/spec_index.py`'s own shape: a `parse()` of `requirements.md`'s
`## R###` blocks (reusing the field names already documented there —
`quote`, `source_issue`, `check`, `status`), a `render()` that emits
the condensed line list plus a header stating the source file and the
regeneration command, and a `--update` mode that overwrites the digest
file. Size is O(requirement count) by construction — it derives only
from `requirements.md`, never from the record tree — directly
answering the survey's discriminating assumption test.

**2. Auto-maintenance — commit-time regenerate-or-deny.**
New `on-the-record/hooks/requirement-digest-preflight.sh`, wired into
`hooks.json`'s existing `PreToolUse`/`Bash` group (same group as
`spec-index-preflight.sh`). Same contract as that hook: on a `git
commit`, if the staged diff touches `docs/specs/requirements.md`, the
hook recomputes the expected digest content from the staged blob
(`git show :docs/specs/requirements.md`) and DENIES the commit unless
`docs/specs/requirement-digest.md` is staged with matching content —
forcing whichever session appended a requirement to regenerate the
digest in the same commit, with no separate skill invocation and no
CI. `gates/requirement_digest.py` (the check-mode counterpart, wired
into `gates/ci.py` next to `gates.requirement_registry`) re-runs the
same comparison against HEAD as a CI-timing backstop, matching
`spec_index.py`'s own two-timing (hook pre-commit, gate at CI) split.

**3. Drift guard — advisory, watch-class, board-wide.**
Add `requirement_drift()` to `spawn.py`, called from the same
`_board_wide_sweep()` site as the existing `accumulation_trend()` call
(`docs/specs/enforcement-boundary.md`'s own precedent row for
"advisory (non-blocking) ... board-wide, cross-session view"). Per
tick: read the live requirement IDs from `requirement-digest.md`
(status `open`/`enforced`, excluding `stale`); scan currently open
issues/PRs (already-available `gh` data the board-wide sweep already
touches) for a `northpole req#<n>` mention or an `R###` trailer;
report, as plain advisory lines (never a blocking exit), (a) any
digest requirement with zero referencing open issue/PR this tick, and
(b) any open proposal/PR whose body cites no digest requirement ID at
all. This is a report only — per the watch-class inviolable principle
`enforcement-boundary.md` already documents for `accumulation_trend()`,
it never blocks a commit, merge, or session.

**4. Zero-onboarding pointer (req#2).**
One line added to `on-the-record/hooks/directive.sh`'s existing
`UserPromptSubmit` output: name `docs/specs/requirement-digest.md` as
the one file that condenses the full live requirement set, so a fresh
session sees the pointer on its very first prompt with no explicit
invocation — same delivery channel `directive.sh` already uses for
every other standing directive.

## Out of scope

- Rewriting `requirements.md` itself or its registration workflow —
  unchanged; the digest derives from it, never replaces it.
- Making the drift guard blocking — explicitly rejected: req#6's own
  text asks for "advisory 가능" and the watch-class inviolable
  principle this repo already documents forbids a watch-shaped check
  from blocking.
- A digest that reconstructs per-issue narrative detail (candidate C)
  — rejected above on RICE grounds; the digest is a condensation, not
  a second copy of each issue's record.
- Any GitHub Actions/CI-only wiring — the digest's authoritative
  enforcement point is the commit-time hook; `gates/ci.py`'s copy is a
  backstop, not the primary mechanism, per req#7.
- Implementation itself (phase 2, pending approval): writing
  `gates/requirement_digest.py`, the new hook, the `spawn.py` addition,
  their tests, and the harness fixture below.

## How you will know it worked

Per the issue's own acceptance section, in `harness/`, a new
`fixture-requirement-digest` scenario, following the existing
`harness/fixture-*` + `harness/driver.py` pattern:

1. **Seed**: append several synthetic entries to a scratch copy of
   `requirements.md` across multiple commits, alongside many synthetic
   `docs/issue-*` records/PR bodies (deliberately record-count >>
   requirement-count, to exercise the O(requirement-count) claim).
2. **Digest reflects the live set**: assert `requirement-digest.md`
   (after `gates/requirement_digest.py --update`) lists exactly the
   `open`/`enforced` entries from the seeded registry, in a line count
   equal to the requirement count, not the record count; assert the
   commit-time hook DENIES a commit that edits `requirements.md`
   without regenerating the digest, and ALLOWS one that does.
3. **Fresh session, digest-only**: spin a fresh harness session whose
   only supplied context is `requirement-digest.md` (no issue history,
   no other reports — same "zero onboarding" bar req#2 sets); assert
   the next task it selects cites one of the digest's still-`open`
   requirement IDs, demonstrating goal-aligned selection from the
   digest alone.
4. **Drift guard fires, advisory**: seed one digest requirement with
   zero referencing open issue/PR and one open proposal citing no
   requirement ID; assert `requirement_drift()`'s board-wide sweep
   output names both as advisory findings, and assert (separately)
   that neither finding blocks the sweep's own exit code or any commit
   — the non-blocking half of the acceptance bar.

Empty state: an empty `requirements.md` (no entries) → digest renders
a single documented empty-state line, never a blank file and never a
gate crash; a board-wide sweep with no open requirements and no open
work → the drift guard emits its own "nothing to compare" line rather
than silence, matching `roster_watchdog()`'s existing empty-state
convention.

Wiring check (req#7): `check_body`-style verification that the new
hook lives under `on-the-record/hooks/` and is registered only in
`hooks.json`'s `PreToolUse` block — `.github/workflows/` stays
untouched by this change, asserted directly in the harness run.

## Accumulation

Accumulation-cost-shaped: the digest's own cost profile is the point
of the design. `gates/requirement_digest.py`'s render cost is O(number
of `## R###` entries in `requirements.md`) per regeneration, and
regeneration only fires on commits that touch `requirements.md`
(bounded by how often requirements are actually added, not by total
record volume). The drift guard's per-tick cost inside
`_board_wide_sweep()` is O(open issues/PRs) for the reference scan —
the same order of magnitude `accumulation_trend()` already pays on
that same tick — plus O(digest requirement count) for the comparison,
so no new cost order is introduced beyond what the existing sweep
already runs every cycle. No cost in this design scales with the total
historical record count (issues/PRs/reports ever created), which is
the specific accumulation failure mode #930 names.
