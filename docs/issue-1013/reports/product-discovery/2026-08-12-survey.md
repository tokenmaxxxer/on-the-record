## Background / context

`on-the-record`'s `spawn.py` keeps machine-global state under
`~/.tokenmaxxxer/work` (or the repo-local `runs/` tree): a JSON roster of
live role sessions (`ROSTER` / `runs/active.json`), a watchdog scan over
that roster, and a spawn-time gate that blocks a new spawn when other
`issue-*/` PRs are still undisposed. issue-1013 is an operator report from
2026-08-12 describing four concrete cross-session leaks observed while
running multiple orchestrator sessions on one machine.

**1. "board/watchdog reports include ALL role sessions, not its own."**
canonical: spawn.py:2469-2497 (read this session). `roster_watchdog()`
loads the full roster with `d = _roster_load()` (spawn.py:2494) and then
`for key, e in sorted(d.items())` (spawn.py:2497) with no filter on
`e.get("session_id")` against the calling orchestrator's own
`ORCHESTRATOR_SESSION_ID_ENV`. Every live entry in the shared `ROSTER`
file is scanned and printed. No ownership filter exists on this path
today, per the cited read of spawn.py:2469-2497.

**2. "undisposed-PR spawn gate blocks a session's spawn because a
DIFFERENT session's PR is open."**
canonical: spawn.py:1154-1179 (read this session). `_undispositioned_role_prs()`
calls `_open_role_prs()` (repo-wide `gh pr list --state open`, no session

`exclude_issue` (spawn.py:1174, "진행 중인 그 이슈 자신을 막지 않는다" — skips

open `issue-*/` PR opened by any orchestrator session, past or present,
blocks the new spawn unless the `--despite-returned` bypass flag is
supplied (spawn.py:4494, read this session). This gate has no
session-scoping surface today, per the cited read of spawn.py:1154-1179 —
ownership here has to be approximated (e.g. via the roster entry that
produced the PR's branch), not read directly off the PR, since a PR
carries no session_id of its own.

canonical: gh issue view 1013 (read this session, symptom 3 quote below).

**3. "watchdog --auto-respawn re-spawned issue-791's session after
another flow had already disposed of its PR."**
canonical: spawn.py:2513-2551 and spawn.py:3165-3199 (read this session).
The dead-entry branch inside `roster_watchdog()` (spawn.py:2513, `if not
_alive(e.get("pid", 0))`) runs for every dead roster entry regardless of
`session_id`, and calls `_auto_respawn_check(key, e, respawn_state)`
(spawn.py:2550) when `auto_respawn=True`. `_auto_respawn_check()` itself
(spawn.py:3165-3199) takes no session identity as input — it derives
`crashed`/`stalled` purely from `session_end_verdict(work, log_path)`
(spawn.py:3177) and, on `crashed`, unconditionally calls
`_respawn_or_cap()` (spawn.py:3198). The one PR-disposition check in this

None` / `_maybe_resume_for_ready_pr` resume branch (spawn.py:2545-2549),
not on the auto-respawn branch that follows it (spawn.py:2550) — per
this same cited read, the auto-respawn branch does not re-check PR state
immediately before respawning. Auto-respawn scans and acts on entries
irrespective of which session's scope they belong to, on the cited read

**4. "watcher-dead anomalies cite pids from watchers armed by other
sessions/earlier turns."**
canonical: spawn.py:1861-1888 and spawn.py:1916-1955 (read this session).
`_watcher_looks_real()` already keys stale-watcher detection to `issue` +
`role` via `/proc/<pid>/cmdline` (spawn.py:1875-1885, per issue #559's
after-proposal hunt finding cited in the function's own docstring at
spawn.py:1869-1872) — watcher identity by cmdline content, not by which
orchestrator armed it. `roster_ps()` (spawn.py:1916, the code path that
prints `워처: DEAD(pid ...)`/`UNWATCHED`) reads `watcher_pid` from
`ws_idx` (the workspace index, spawn.py:1938-1941) with no session_id

it still carries no session-ownership axis, per the cited read of
spawn.py:1916-1955, so a watcher armed by a *different* session for the
*same* issue+role (e.g. a respawn from another orchestrator) reads as
this session's own watcher.

## Existing scoping primitive: `session_id`

canonical: spawn.py:5427, 5516 (read this session). Every roster entry
already carries `"session_id": os.environ.get(ORCHESTRATOR_SESSION_ID_ENV)
or None` at registration time (both the pre-registration stub at
spawn.py:5427 and the main registration at spawn.py:5516). This is the
*spawning orchestrator's own* session id (harness-supplied), not the
child role session's id — exactly the field the issue names as "already
stored per entry as session_id." It can be `None` when the harness driver
does not set `ORCHESTRATOR_SESSION_ID_ENV` (spawn.py:46 defines the env
var name), per the same cited read — the single-session / no-driver-env
case, which matters for the empty-state acceptance criterion: on a
machine/session where this env var is never set, every entry's
`session_id` is `None`, so an "own entries" filter keyed on exact
`session_id` equality must treat `None == None` as a legitimate
self-match (today's default behavior), not as "no owner, hide it."

## JTBD tuple (problem stated without a solution attached)

- **Job performer**: an operator running two or more on-the-record
  orchestrator sessions concurrently on one machine (e.g. one per issue),
  each spawning and watching its own role sessions.
- **Job**: monitor and act on the role sessions *this* orchestrator
  session spawned — see their status, get gated only by their own
  in-flight work, get notified/respawned only for their own crashes —
  without being confused by, blocked by, or accidentally duplicating
  another concurrent session's work.
- **Circumstance**: `spawn.py`'s roster, watchdog state, and workspace
  index are machine-global JSON files (`~/.tokenmaxxxer/work`), written
  and read by every orchestrator session on the box with no partitioning;
  concurrent sessions are a normal, not exceptional, operating mode (the
  issue's own four symptoms are from one real day of concurrent use, per
  the issue's dated "Operator report (2026-08-12)" section, canonical:
  gh issue view 1013).
- **Desired outcome**: each session's poll-report, gate, and
  auto-respawn decisions are scoped to what it owns by default, while
  no orphaned entry (a dead session's still-unwatched work) silently
  disappears from view for anyone.

The issue text already names the solution shape (own-entry scoping +
`--all` view + orphan surfacing) fairly precisely; restated in JTBD terms
above, the underlying job is "let me manage my own fleet without
cross-talk," and the observation-loss invariant in the ask is the
guardrail on that job, not a separate feature.

## Opportunity-solution tree branch

- **Tree outcome**: operators run several concurrent on-the-record
  orchestrator sessions on one machine without cross-session interference
  in what each session sees, is gated by, or auto-acts on.
- **Opportunity**: four points where machine-global state currently
  leaks across sessions — watchdog poll-report scope (symptom 1), the
  undisposed-PR spawn gate's exclude-set (symptom 2), auto-respawn's
  scan-and-act loop (symptom 3), and watcher staleness detection's
  identity key (symptom 4) — plus one out-of-scope logging seam
  (symptom 5, lives outside spawn.py).
- **Candidate solutions**: (a) filter `roster_watchdog()`'s iteration to
  entries whose `session_id` matches the calling orchestrator's own
  `ORCHESTRATOR_SESSION_ID_ENV` by default, with orphaned entries (dead
  owner, i.e. owning session no longer resolvable/alive) always surfaced
  regardless of scope; (b) extend `_undispositioned_role_prs()`'s
  exclusion to also exclude PRs whose branch traces back to a roster
  entry (live or recently-dead, orphan-checked) owned by the calling
  session — approximate via branch-name -> roster-key -> session_id, since
  PRs carry no session_id of their own; (c) scope `_auto_respawn_check()`'s
  dead-entry loop the same way as (a), with orphan entries surfaced (not
  silently acted on) rather than auto-respawned by a session that did not
  own them; (d) add a `session_id` join to `roster_ps()`/watcher-staleness
  reporting so a watcher armed by a different session for the same
  issue+role reads as "other session's watcher," not this session's own.
  All four route through one shared primitive: an "own entries" filter
  function keyed on `session_id` equality (`None == None` included, for
  the empty-state/no-env-var case), plus an explicit `--all` bypass and
  an orphan-surfacing sweep (dead pid + session_id whose owning session
  process is itself unresolvable) that runs unconditionally.
- **Discriminating assumption test**: `tests/test_spawn.py` gains a
  two-session-scoping case per the issue's own acceptance — two roster
  entries with distinct `session_id`s, asserting default `watchdog`/gate/
  auto-respawn calls touch only the entry matching the caller's own
  `ORCHESTRATOR_SESSION_ID_ENV`, `--all` surfaces both, and an entry whose
  `session_id`'s owning process is dead surfaces as orphaned under
  default scope instead of being silently dropped. This test does not
  exist yet; it is proposed in the companion proposal, not yet built.

## Existing conventions this composes with (not re-derived)

- `_watcher_looks_real()`'s issue+role cmdline identity check (#559) —
  the ownership axis proposed here is additive to this, not a
  replacement: watcher staleness stays keyed on issue+role+cmdline
  liveness, and session ownership is a separate filter on top for
  *reporting* scope.
- `_maybe_resume_for_ready_pr()` / `_session_resume_claim()` (#878) —
  already reads `entry.get("session_id")` to decide whether to fire a
  `--resume` nudge; this is the one place in today's code that already
  branches on `session_id`'s presence, and is the nearest existing
  precedent for "session_id-keyed behavior" the proposal extends.
- `--all` flag (already defined for `watch --all`, spawn.py:4497-4499,
  issue #488) — the issue's ask for "an explicit `--all` view" should
  reuse this flag's name for `watchdog`/other roster-scanning
  subcommands rather than inventing a second flag with the same meaning,
  since argparse already treats `--all` as a single shared boolean across
  subcommands in this file.
