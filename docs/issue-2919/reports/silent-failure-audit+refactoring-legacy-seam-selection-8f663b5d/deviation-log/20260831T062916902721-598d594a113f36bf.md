# Deviation log — issue-2919 (silent-failure-audit+refactoring-legacy-seam-selection-8f663b5d role)

- 2026-08-31T06:00:00Z | inline | first attempt at the real-bash-3.2 concurrency proof launched each of the 8 workers as its own separate `docker run` container. This produced clean-looking results (no logged critical-section overlaps), but the setup was not trustworthy for the `alive`/`dead` liveness checks: separate `docker run` invocations get separate PID namespaces, so `kill -0 <pid>` from one worker's container checking another worker's recorded pid checks an unrelated process table. The atomic-noclobber-write mutual-exclusion property itself (a pure filesystem guarantee) was not invalidated by this mistake, but the result was not trustworthy as proof of the liveness-check branches. Rebuilt as a single `docker run --init` container running all workers as real background sibling processes sharing one PID namespace before trusting the result. canonical: `docs/issue-2919/reports/silent-failure-audit+refactoring-legacy-seam-selection-8f663b5d.md` "What did not work", this session.
- 2026-08-31T06:00:00Z | inline | the same per-worker-container setup broke the crash-recovery proof entirely at first, for an unrelated reason: `kill -9 $$` where `$$` was the container's own PID-1 process did not terminate it (Linux's PID-namespace-init signal special-casing ignores default-action signals for a namespace's PID 1 unless something like `docker run --init` inserts a real init as PID 1). Confirmed via `docker run --rm bash:3.2 bash -c 'kill -9 $$; echo after'` printing `after`, versus the same command with `--init` producing container exit code 137 and no further output.
