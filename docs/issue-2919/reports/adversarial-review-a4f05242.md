## Open findings

- **The mkdir-based mutex's stale-lockdir break path can break a live, merely-slow holder's lock, not just a genuinely-stale/abandoned one, and the recovering worker proceeds into the critical section without re-acquiring its own lock.** canonical: point 10 above, live-timestamped reproduction (`/tmp/mutex_attack.sh`, this session): A held 203.23-228.24, B broke A's lock at 222.66 and ran 222.67-223.68, entirely inside A's window. Resolution path: not a revert (the mkdir-mutex design itself is sound for the common uncontended case, confirmed in point 9 with `max_concurrent_holders_observed=1` across 8 concurrent writers) — a follow-up should either record the holder's PID inside the lockdir and only break it after confirming that PID is actually dead (`kill -0`), or have the recovering worker `mkdir` its own fresh lockdir after the break rather than falling through unprotected, or both. Given `_alive_stamp_write()` runs every 120s and each write is sub-millisecond in the uncontended case, a real 20s+ stall is an unlikely but not impossible event (a loaded host, a slow/network filesystem); the current code handles that event incorrectly rather than not at all.
- **The new `[patrol-poll] skills query failed at startup, patrol skipped this tick` line is unconditional, un-suppressed, and — because `spawn.role_data()` is permanently absent today — fires on literally every session's every patrol-due tick (every ~10 minutes by default), starting immediately on merge, reintroducing the class of notification noise issue #2906/PR #2913 removed.** canonical: point 11 above — derived: 4-tick live run of the real PR-head script against the real (unmodified) `spawn.py`, this session, result: the line printed on all 4 ticks verbatim. Resolution path: this is issue #2925's problem to resolve (remove the whole patrol subsystem, per its already-recorded operator decision, confirmed via `gh issue view 2925` this session), not this PR's — but this PR's own description and record should state the concrete, immediate consequence ("every session, every ~10 minutes, until #2925 lands") in plain terms for a merge-time reviewer, rather than only the abstract "the query has always failed" framing. Given #2925's acceptance criteria explicitly forbid weakening this line before removal, the correct path is to land #2925 promptly rather than change #2923's already-merged behavior.
- **The PR's own explanation of the line-336-vs-295 discrepancy is imprecise in its wording** ("the loop's closing `done` line" reads as the immediately-enclosing `for` loop's own `done`, at line 322, but the actual crash — reproduced live — reports the *outermost* `while` loop's `done`, at line 336). canonical: point 3 above — derived: live docker reproduction against the `origin/main` worktree, this session, result: `on-the-record/monitors/poll-heartbeat.sh: line 336: POLL_HEARTBEAT_PATROL_SKILLS[@]: unbound variable`, cross-checked against `grep -n 'for _patrol_skill\|done'` showing the `for` loop's own `done` at line 322 and the outer `while` loop's `done` at line 336 (the file's last line).
