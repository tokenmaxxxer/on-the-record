## Why

**mkdir-lock over alternatives for the flock fallback.** Considered and rejected: (a) requiring/vendoring a `flock`-equivalent binary — forbidden outright by the issue's must-not ("must not require macOS users to install util-linux or a newer bash"); (b) dropping the lock and writing unserialised on hosts without `flock` — this is exactly the pre-existing defect the issue reports ("a lock that does nothing while reporting success"), and the issue's must-not is explicit that this must not be silently accepted; (c) a lockfile keyed by `open(O_EXCL)` via a small inline Python one-liner — works, but spends a `python3` fork per lock acquisition on a path that already runs every 120s, and `mkdir`'s atomicity guarantee is identical without spawning anything. `mkdir` was chosen because it needs zero new dependencies, is atomic on every POSIX filesystem (including macOS's), and costs one syscall in the uncontended case (the overwhelmingly common one) — no measurable overhead added to the per-tick path when there is no contention, and the flock-present path (the common Linux/CI host) is completely untouched.

**Separate exit-code capture over "just declare the array first" for the unbound-variable fix.** `POLL_HEARTBEAT_PATROL_SKILLS=()` declared ahead of the `read -a` was considered and rejected first, because it does not actually fix the crash: live reproduction (item 2 above) showed a **declared, empty** array still raises `unbound variable` under `set -u` on bash 3.2.57 — this is a genuine bash <4.4 quirk (fixed in 4.4), not merely an unset-name problem, so pre-declaring the array alone would have left the crash in place. The `${NAME[@]+"${NAME[@]}"}` guard was chosen because it is the standard portable idiom for exactly this bash-version gap and needed no restructuring of the surrounding loop. Capturing the query's exit code separately (rather than accepting empty-output-either-way) was necessary specifically because the issue's must-not forbids conflating "genuinely empty" with "failed query" — a plain `2>/dev/null` discard (the original code) cannot make that distinction; capturing `rc` and `stderr` (via `2>&1`) can, and this call runs once at Monitor startup (not per tick), so the extra capture costs nothing against the per-tick overhead constraint.

## What did not work

The first version of `t_patrol_skills_query_failure_is_visible_issue_2919` used the pre-existing `FAKE_SPAWN_PY` fixture (the one `_make_checkout()` writes) expecting it to reproduce a *failed* `role_data()` query via `AttributeError`. derived: diagnosed by running the exact env under `bash -x on-the-record/monitors/poll-heartbeat.sh` directly (not the pytest harness), this session — result: trace showed `_patrol_skills_query_rc=0` where a nonzero rc was expected.
