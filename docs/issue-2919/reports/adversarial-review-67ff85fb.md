**1. A third, undisclosed residual: the max-age valve's evicted holder releases the lock it no longer owns, and can hand a live third holder's active lock to a fourth contender (highest-severity finding, confirmed by live reproduction).**

PR #2948 discloses two residuals: the sub-syscall `open()`/`write()` gap inside the single noclobber command, and the max-age valve's own stated trade-off ("if a holder is still genuinely alive and legitimately working past 60s ... the valve force-reclaims it anyway and a second writer proceeds concurrently"). Per the task's fourth attack point, I looked for a third the PR did not name, rather than re-confirming those two.

Reading `on-the-record/monitors/poll-heartbeat.sh` (commit `c5ebd0e3`) lines 350-357 (`_alive_stamp_write`'s no-`flock` branch, this session, Read tool): once a holder exits its acquire loop (whether by winning the noclobber race outright, or by having *someone else's* max-age valve force-reclaim a slot it then re-acquires), it always finishes with:
```bash
printf '{"last_tick": %s}' "$(date +%s)" >"${_alive_stamp_path}.tmp" 2>/dev/null \
  && mv -f "${_alive_stamp_path}.tmp" "${_alive_stamp_path}" 2>/dev/null
rm -f "${_lockfile}" 2>/dev/null || true
```
This final `rm -f` is **unconditional** — it never reads the lockfile back to confirm it still names `$$` before removing it. That is a structurally identical omission to the one `adversarial-review-95d4569a` found and this PR fixed in the acquire path (no re-verification before acting), just moved to the release path instead.

This is exploitable via the max-age valve itself, which this PR adds: the valve's own disclosed trade-off already establishes that a genuinely-alive holder (call it A) can be force-reclaimed by a waiter (B) while A is still actually running. The PR frames this as "a second writer proceeds concurrently" — a one-time, bounded cost against A. What the PR does not disclose: when A eventually finishes its real work and reaches its own unconditional `rm -f "${_lockfile}"`, that removes **whatever currently occupies that path** — which by then may be a completely unrelated third holder B's still-active lockfile, not A's own (already-deleted-by-the-valve) slot. A fourth contender D, polling normally with no self-triggered valve of its own, then sees an empty lockfile, wins the noclobber race, and enters the critical section concurrently with B — the exact unprotected-concurrent-write failure shape issues #2923/#2919 exist to close, reintroduced through a path the PR's own disclosure does not cover (it only describes A-vs-B colliding once, not A's later release cascading onto an unrelated B-vs-D pair).

## Open findings

- **The max-age valve's evicted-but-still-alive holder releases the lock unconditionally on its own eventual completion, without re-checking ownership — this can hand a live, unrelated third holder's active lock to a fourth contender, reproducing the exact unprotected-concurrent-write failure this whole issue chain (#2923 → #2935 → #2948) exists to close.** canonical: "What was done" finding 1 above, live-reproduced inside a real bash-3.2/no-`flock` container this session (`PRE_RELEASE_OWNER_CHECK` instrumentation showing A remove B's active lockfile, D entering concurrently with B from `565` to `567`). Resolution path: the same fix the acquire side already received (adversarial-review-95d4569a point 1, this PR's own headline fix) needs to apply symmetrically to the release side — read `${_lockfile}`'s current content back and compare to `$$` immediately before the final `rm -f`, and skip the removal (log it distinctly, per silent-failure-audit) if it no longer names this process, rather than removing unconditionally. This is not a revert candidate: the forming-window fix (finding 2, atomicity) and the valve's core recovery-from-zombie property (finding 4) are both independently confirmed sound; this is a second, narrower gap in the same function, not a defect in what was already fixed.
