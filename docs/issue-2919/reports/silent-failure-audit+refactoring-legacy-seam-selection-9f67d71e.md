## What was done

canonical: `docs/issue-2919/reports/adversarial-review-a4f05242.md` (commit `00143ce89d484521002993d0d08fe0428b3be607`), "Open findings" point 1, read this session. Fixed the mutual-exclusion defect independent review found in PR #2923's mkdir-based mutex: the old stale-lockdir break path forced `rmdir` after exactly 20 failed one-second mkdir retries, regardless of whether the current holder was still running. A holder merely slower than 20s (a loaded host, a slow filesystem) had its lock broken and re-entered by a second worker while still inside its own critical section -- the review reproduced this live (worker A held 25s, worker B broke A's lock at the 20s mark and ran concurrently inside A's still-open window). The old code also fell through into the critical section *without re-acquiring* after breaking a lock, so the "recovering" worker itself ran unprotected.

The fix (`on-the-record/monitors/poll-heartbeat.sh`):

1. **Sprouted `_alive_stamp_lock_owner_status(lockdir)`** (new function, ~30 lines with its design-rationale comment) -- establishes liveness via the lock holder's own recorded PID and `kill -0` (a same-host signal-0 existence probe), rather than inferring staleness from elapsed retry count. Returns exactly one of `alive` / `dead` / `forming` (lockdir exists but the holder hasn't recorded its PID yet -- the narrow acquire-then-write-pid window).
2. **The holder now records its own PID** (`printf '%s' "$$" >"${_owner_pid_file}"`) immediately after a successful `mkdir`, and removes that pid file before its own final `rmdir` on release.
3. **The retry loop's `case` on that verdict**:
   - `alive` -> never breaks the lock, resets the forming-grace counter, loops back to `sleep 1` and retries -- unbounded wait, no matter how many retries have elapsed. This is the actual fix: the old unconditional 20-try-then-break threshold is gone entirely for a holder proven alive.
   - `dead` -> reclaims (`rm -f` the pid file, `rmdir` the lockdir) immediately once confirmed, logs the reclaim with the confirmed-dead PID via `_poll_watchdog_log_append` (silent-failure-audit: the reclaim is never silent), and loops back to retry `mkdir` -- fixing the second defect the review flagged (the old code fell through into the critical section unprotected after breaking a lock; the new code always requires a fresh successful `mkdir` before proceeding).
   - `forming` -> a short (3-retry / ~3s) grace period before treating an owner that never recorded a PID as abandoned, since there is no PID left to confirm dead in that state; also logged on reclaim.
4. Added three permanent regression tests to `on-the-record/monitors/test_poll_heartbeat.py`. derived: `git diff origin/issue-2919/silent-failure-audit+refactoring-legacy-seam-selection-4495e32f -- on-the-record/monitors/test_poll_heartbeat.py | grep -c '^+def t_'` (this session) -> 3 new test functions added, 0 existing lines removed or modified (same diff shows no `-def t_` lines): a fast deterministic unit test of the sprouted liveness function (alive/dead/forming), and two live-concurrency tests that dynamically extract the real function bodies out of the current script text (never a hand-copied fork, so they cannot silently drift from the implementation) and run them as real concurrent OS processes with an artificially-widened critical section, mirroring the adversarial review's own harness shape.

## Why

**Design choice -- PID + `kill -0` over a longer/adaptive timeout.** The defect's root cause was inferring death from elapsed time; any fix that kept a time-only heuristic (even a longer or backoff-based one) would still be wrong in kind, just wrong less often. Recording the actual holder's PID and checking it directly establishes liveness rather than guessing it, which is what the task explicitly required ("the holder's liveness must be ESTABLISHED, not inferred from elapsed retries"). This also fixed the second, related defect for free: since reclaiming now loops back to retry `mkdir` instead of falling through, a recovering worker always re-acquires its own lock.

**Seam choice -- Sprout Method, not a full object seam or a rewrite of the retry loop.** Per refactoring-legacy-seam-selection rule 4 (confidence/budget, not aesthetics): the surrounding legacy code (the flock branch, the tick loop, the patrol machinery) is correct and out of scope; a full seam/characterization pass over the whole file was not warranted for a single, clearly-localized behavioral change. Sprouting the liveness check as its own function (rule 1) gave it an independent unit test without touching or re-characterizing anything else, and rule 6 kept the seam narrow -- only the stale-lockdir branch of `_alive_stamp_write`'s no-flock path changed; the flock branch, `while` loop structure, and every other function are byte-for-byte unchanged outside the diff. derived: `git diff origin/issue-2919/silent-failure-audit+refactoring-legacy-seam-selection-4495e32f -- on-the-record/monitors/poll-heartbeat.sh` (this session) shows every changed hunk confined to the `_alive_stamp_lock_owner_status` addition and the no-flock branch of `_alive_stamp_write`; no other function's lines appear in the diff.

**Residual race windows -- stated precisely, not claimed away.** Two remain, both far narrower than the 20s window this fix closes:
1. **PID reuse.** If a holder crashes and the OS reuses its exact PID for an unrelated live process before a challenger's `kill -0` check runs, the challenger will read that PID as alive and wait indefinitely for a lock that will never be released by its recorded owner. Cost: an indefinite wait on that one alive-stamp write until an operator manually clears the lockdir, or until the reused-PID process itself exits -- never a silent double-entry, which is the defect actually being fixed. Given typical PID-space reuse cycles and the short (sub-millisecond in production) critical section, this is a low-probability event, but not zero; documented here per the task's instruction not to claim an unqualified guarantee.
2. **The "forming" grace boundary.** If the true gap between a holder's `mkdir` and its own PID write is ever legitimately slower than the 3-retry (~3s) grace period (an extremely loaded host pausing the holder in that exact narrow window), a challenger could reclaim a lock whose holder was about to record its PID and enter normally. This is the same class of risk the original 20s-blanket window had, but scoped down by roughly an order of magnitude (~3s vs. 20s) and to a much smaller slice of the holder's lifetime (the acquire-to-pid-write gap only, not the whole critical section).
3. **Zombie processes, observed during this fix's own test-writing (not a production concern, documented for completeness):** `kill -0` reports a zombie (an exited-but-unreaped child) as still existing. This surfaced while writing `t_alive_stamp_mutex_recovers_crashed_holder_issue_2919` -- see "What did not work" below for the concrete reproduction and fix. This is a real, generic limitation of PID-based liveness checks, not specific to this script -- in production, poll-heartbeat.sh instances are peers, not parent/child of each other, so a crashed peer's zombie lifetime is governed by whatever process actually spawned it (typically reaped promptly), not by another writer failing to call `wait()`.

## What did not work

canonical: this session's own test-run transcript. The first version of `t_alive_stamp_mutex_recovers_crashed_holder_issue_2919` hung past its 15s subprocess timeout on every run (`subprocess.TimeoutExpired` after 15s, reproduced 2x standalone). Root cause, found via `/proc/<pid>/wchan` inspection this session: worker A (simulating a crash via self-`kill -9`) was left unreaped by the Python test harness (nothing called `.wait()`/`.poll()` on it), so `kill -0` kept reporting it as a live zombie -- residual-race item 3 above. derived: a manual reproduction with A deliberately left unreaped for 20s showed the reclaim only fired at the 21s mark, immediately after a `.poll()` call elsewhere in the debug script finally reaped A -- confirming the zombie, not the mutex logic, was the cause. Fixed by reaping A in a background thread (`threading.Thread(target=proc_a.wait, daemon=True).start()`) immediately after starting it, matching realistic process-supervision behavior (a real crashed writer's own parent reaps it, not another writer). derived: `python3 on-the-record/monitors/test_poll_heartbeat.py`, this session, re-run 3x after the fix -> `41/41 passed` each time, ~3-4s completion for that test each run.
