The commit intended to land `on-the-record/hooks/amendment_channel.py`,
`amendment-channel.sh`, `hooks.json`, `hook_classification.json`, and
`test_hook_classification.py` together (all five were `git add`-ed) hit
two `gate-registration-guard` PreToolUse refusals in a row (missing spec
rows, then a classification mismatch) before landing successfully as
`593256bb`. Only the two files touched by the second fix round
(`amendment-channel.sh`'s files plus `docs/specs/generated-paths.md`)
were re-`git add`-ed before the final commit attempt — `hooks.json`,
`hook_classification.json`, and `test_hook_classification.py` did not
carry forward into that commit despite still showing as staged in
earlier `git status` output, so the actual hook registration silently
did not land in the branch history for two more commits (probes, unit
tests) until a routine `git status`/`git diff --cached --stat` check
before the next commit caught the discrepancy — canonical: `git show
--stat 593256bb` (checked at the time) showed only 3 files instead of
the expected 5. Fixed by re-staging and committing the three missing
files as `61065ede`, verified via `git diff --stat` (empty) against a
clean working tree before proceeding. No data was lost — the working
tree copies were correct the whole time, only the commit boundary was
wrong — but this is exactly the "staged but not actually landed" gap
the completion-and-landing directive warns about, so it is recorded
here rather than silently folded into the next commit's description.
