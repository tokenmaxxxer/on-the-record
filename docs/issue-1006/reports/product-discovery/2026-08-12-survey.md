## Background / context

`on-the-record` runs an installed orchestration session (`directive.sh`,
injected every `UserPromptSubmit`) that turns a user's requirement into an
issue, spawns role sessions against it, and relays PR outcomes. issue-1006
asks whether five operator-facing properties of that session already exist,
partially exist, or are missing, and what to build for the gap.

## Per-sub-requirement coverage (read evidence)

**1. Role-verified achievement (not self-assessed).**
canonical: on-the-record/hooks/directive.sh:171-186 (read this session).
`directive.sh:171-186` ("AUTONOMOUS ASYNC COMPLETION") routes completion
through role output: the orchestrator's own next action after a
notification is stated as "verify it (read the diff and checks, the same
acceptance judgment `/orchestrate:run` step 6 already defines)" before
merge, and the merge criterion is a role-produced, mergeable PR rather than
the orchestrator's self-report.
canonical: docs/handbooks/async-completion-drive.md:52-59 (read this
session). The 4-part `final_report` there is likewise built only from a
resumed role-driven turn, with the file's own text stating it is never
constructed on a break in the chain.
Existing coverage of req#1 looks substantial on this reading. Gap:
neither file states that the verification step must trace back to the
requirement text itself (issue → role verdict), as opposed to "PR is
mergeable" alone — `requirement-digest.md` already holds a requirement list
this could anchor to, but directive.sh's AUTONOMOUS ASYNC COMPLETION
section does not cite it.

**2. Full-delegation default mode.**
canonical: on-the-record/hooks/directive.sh:139-166 (read this session).
`directive.sh:139-148` ("DELEGATION IS THE DEFAULT", issue #699 R2) and
`:149-166` ("YOUR GOAL LOOP", #699 R3) state the default behavior as
decompose → delegate every judgment to consult, every artifact to a spawned
role → integrate → continue, with no explicit skill call required. Existing
coverage of req#2 looks substantial on this reading. Gap:
canonical: on-the-record/hooks/directive.sh:32-33 (read this session). the
loop's entry point still assumes a requirement is already issue-shaped —
directive.sh's own opening line reads "Requirements become ISSUES you draft
and the user confirms" — and has no branch for an opening ask not yet
precise enough to draft an issue from. That is sub-requirement 4's gap, not
2's.

**3. Interaction guidance (session teaches the user how to work with it).**
`directive.sh`'s entire body is orchestrator-facing procedure — it never
addresses the user directly, and nothing in it is gated on "is this the
first message of the session."

```

```
derived: command above; no output.

No first-contact/onboarding hook exists under `on-the-record/hooks`. This
sub-requirement is open.

**4. Requirement elicitation support.**
`directive.sh` states the requirement-capture step (its own text: "you are
the scribe, never the inventor") but has no branch for a vague/incomplete
ask — no reference to the `user-discovery` or `requirements-quality`
skills, no clarifying-question trigger, on the same read as req#2/#3 above.
This sub-requirement is open as a directive-level trigger; the skills
themselves already exist and are present in this session's own skill
listing (`user-discovery`, `requirements-quality`), so the gap is
composition (when to invoke them), not raw capability.

**5. Progress legibility.**
canonical: on-the-record/hooks/directive.sh:97-105 (read this session).
`directive.sh:97-105` ("REPLY STRUCTURE") mandates flow-anchored narration
on every reply: which issues are in flight and what stage each is at, what
is waiting on the user, and what happens next, illustrated in the file's
own worked example naming an issue number, a flow stage, and a PR number
together rather than a bare item number. This covers the between-replies
case on this reading. Gap:
canonical: on-the-record/hooks/directive.sh:130-137 (read this session).
the TURN-BUDGET RULES section states the turn closes the moment background
work is armed; between arming and the next notification there is no
narration surface at all in the read text — mid-flight visibility depends
on the user asking. This overlaps req#3: nothing tells the user this
pattern exists in advance.

## JTBD tuple (problem stated without a solution attached)

- **Job performer**: an operator running an installed on-the-record session
  against their own target repo, who is not a contributor to on-the-record
  itself and has not read its docs.
- **Job**: state what they want changed, in their own words, and trust that
  it gets built correctly without having to learn the tool's internal
  mechanics (skills, roles, spawn.py, board states) to drive it.
- **Circumstance**: the first message of a session is frequently
  underspecified (a real want, not yet an acceptance-testable requirement),
  and the actual build work happens across multiple backgrounded role
  sessions the operator cannot observe directly.
- **Desired outcome**: the operator always knows, without invoking a skill,
  reading a doc, or asking "what's happening?" — (a) what happens if they
  say something vague, (b) what is happening right now, in their language,
  and (c) that the check on "finished" ran through something other than
  the same process that built it.

The issue text names solutions (directives/hooks, first-contact guidance,
elicitation trigger, progress surface) — restated above in JTBD terms, the
underlying gap is narrower than the issue's five-part solution list: reqs
1, 2, and most of 5 read as already substantially built per the citations
above; only 3 and 4 (plus 5's mid-flight-narration seam) read as genuinely
open.

## Opportunity-solution tree branch

- **Tree outcome**: operators drive real work through on-the-record without
  reading its docs or learning its internal vocabulary.
- **Opportunity**: two moments a first-time operator is currently
  unguided — session start (no self-introduction) and a vague opening ask
  (no elicitation branch) — plus one legibility seam (silence during
  backgrounded work, per req#5's gap above).
- **Candidate solutions**: (a) a first-contact guidance block gated on
  session/conversation-start, appended to `directive.sh`'s existing
  injection; (b) a vagueness-detection branch before "Requirements become
  ISSUES," routing to `user-discovery`/`requirements-quality` skills; (c) a
  narration line at the moment background work is armed (not just at reply
  composition), stating what was armed and what event ends the wait.
- **Discriminating assumption test**: `harness/fixture-operator-experience/
  test_flow.py`, per the issue's own stated acceptance — a seeded vague-ask
  conversation exercised through elicitation → precise requirement →
  delegated run → legible narration → role-verified completion check, and a
  seeded precise-ask conversation exercised straight to delegation
  (empty-state check). This test does not exist yet; it is proposed in the
  companion proposal, not yet built or run.

## Existing conventions this composes with (not re-derived)

- `requirement-digest.md` (#943/#970) — condensed requirement pointer;
  elicitation output should feed into requirements.md the same way, not a
  parallel format.
- deviation loop (#958/#988, `docs/handbooks/deviation-loop.md`) — already
  the pattern for "something needs a decision mid-flow, log it, continue";
  elicitation is a session-start analog, not a new logging shape.
- `final_report` 4-part convention (#878) — already the completion-report
  shape; req#5's "at completion" legibility is this, unchanged.
- `harness/fixture-requirement-digest` — the existing fixture-and-gate
  pairing shape (`gates/requirement_digest.py` +
  `harness/fixture-requirement-digest`) is the structural template for
  `harness/fixture-operator-experience/test_flow.py`.
